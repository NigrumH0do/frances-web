# P09 Rediseño de la web — Plan de implementación

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking. Lee `AGENTS.md` antes de tomar una tarea.

**Goal:** Reemplazar la web v1 (bundle FRB1 + passphrase) por una PWA móvil primero que habla con la API de P08/P10: sistema de diseño propio portado de las maquetas aprobadas (claro/oscuro, AA, 44 px, `prefers-reduced-motion`), sesión por cookie con CSRF, barra inferior Hoy/Temas/Repasar/Chat/Más, cada pantalla con estados de carga, vacío y error, repaso FSRS calculado en el cliente y guardado en el servidor, quiz con los 5 tipos, chat por SSE con «pensando» y cancelar, uso sin conexión con cola de escrituras, y un modo demo para GitHub Pages y los e2e que no necesita servidor.

**Architecture:** Código v2 en carpetas nuevas de `web/src/` (`design/`, `components/`, `l10n/`, `api/`, `offline/`, `auth/`, `shell/`, `review/`, `media/`, `screens/<sección>/`, `demo/`); el código v1 no se edita salvo por tareas CHG (R-31) que extraen núcleos reutilizables (visor PDF, reproductor, práctica, recognizer con token) y cambian la entrada. El cliente de API envuelve un `Transport` con la firma de `fetch`: en producción es `fetch`; en el modo demo (`vite build --mode demo`) es un transporte en el navegador que sirve una instantánea JSON generada **por la API real** sobre los fixtures sintéticos. En el servidor, P09 implementa los dos módulos de rutas que ya reserva `ROUTER_MODULES` (`frances.api.routes.review` y `frances.api.routes.prefs`).

**Tech Stack:** lo de v1 web (React 19.3.1, react-router 8.4.0, Vite 8.3.4, vite-plugin-pwa 2.0.0, ts-fsrs 5.4.2, idb 8.0.4, pdfjs-dist 6.4.299, Speech SDK 1.52.0, Vitest 5.0.4, Testing Library, Playwright 1.64.1) + `@axe-core/playwright` 4.14.0 (dev, MPL-2.0, verificada en npm el 2026-11-02). Servidor: lo de P08 (FastAPI 0.162.0, `TestClient`). Ninguna dependencia nueva de Python ni de runtime web.

**Spec:** `docs/superpowers/specs/2026-11-02-frances-v2-servidor-design.md` (§3 M2 y M6, §7 columna Usuario, §8 completo, §10 presupuestos, §12.4).

## Restricciones del subsistema

- **Propiedad.** Las tareas UI solo crean archivos dentro de sus `owns`. Los archivos de tareas v1 (`web/src/App.tsx`, `main.tsx`, `ui/`, `i18n/`, `data/`, `crypto/`, `routes/`, `srs/`, `pron/`, `sw/`, `vite.config.ts`, `e2e/`, `playwright.config.ts`) se **importan** pero solo los cambian CHG-13…16, con su lista **Touches**. Los módulos v1 puros se reusan tal cual: `srs/scheduler.ts` (`schedule`), `pron/parse.ts`, `pron/stats.ts`, `pron/attempts.ts`, `pron/quota.ts`, `pron/recorder.ts`, `pron/drill.ts`, `ui/pron/score.ts`, `ui/pron/WordList.tsx`, `ui/pron/ScoreSummary.tsx`, `ui/layout/contrast.ts`, `i18n/dates.ts`.
- **Tipos.** Todo tipo de la API sale de `web/src/contracts/generated.ts` (generado desde `contracts/api.schema.json`). Ningún archivo v2 redeclara a mano un modelo de la API; si falta un campo, es un CHG (como CHG-12).
- **Un solo cliente HTTP.** Toda llamada a `/api/*` pasa por `web/src/api/` (UI-04), salvo el chat, que usa `askChat` de AI-16 con el mismo `Transport` y el token CSRF del cliente. Nunca `EventSource`. `credentials: 'same-origin'`; nunca `include`.
- **CSRF y sesión.** El token CSRF vive en memoria (de `Me.csrf_token`) y, tras recargar, se lee de la cookie legible `__Host-frances_csrf`. Va en `X-CSRF-Token` en todo método que no sea `GET`/`HEAD`. La cookie de sesión es `HttpOnly`: el código nunca la lee ni la menciona.
- **Textos.** Interfaz en español. Cadenas comunes en `web/src/l10n/es.ts` (UI-03); cada pantalla tiene su `strings.ts` dentro de su carpeta (sin archivo compartido que todas editen). Fechas con `i18n/dates.ts` (Bogotá).
- **Estilos.** Solo clases y variables de `web/src/design/` (UI-02). La CSP de Caddy (SRV-13) es `style-src 'self'; script-src 'self'`: nada de `<style>` ni `<script>` en línea ni atributos `style` escritos como texto; las props `style` de React (CSSOM) se permiten solo para valores calculados (ancho de una barra de progreso).
- **Estados.** Toda pantalla que lee la API usa `useResource` (UI-04) y `StateView` (UI-03): carga (esqueleto), vacío (texto y acción), error (código traducido y «Reintentar»), sin conexión (dato en caché o aviso). Un test por pantalla cubre los cuatro.
- **Accesibilidad.** Contraste AA en ambos modos (UI-02), objetivos táctiles ≥ 44 × 44 px, foco visible, `prefers-reduced-motion` anula volteo, esqueletos y spinners, navegación con teclado, `aria-live` para resultados (calificación, quiz, chat). El color nunca va solo (README de maquetas, decisión 4).
- **Privacidad.** Ningún texto del curso, email o token en `console.*`, en `localStorage` (salvo `UserOut` del usuario actual para el arranque sin conexión) ni en URLs (el token de invitación va en el fragmento y se borra del historial al leerlo). Cerrar sesión borra cachés de la API, la cola sin conexión y ese `UserOut`.
- **Tests.** Web: Vitest + Testing Library con el transporte falso de `api/testing.ts` (UI-04) y el `renderScreen` de `shell/testing.tsx` (UI-09); sin red. Servidor: `TestClient` y testkit R-35. E2E: Playwright sobre el build demo (UI-22), Chromium y WebKit con viewport móvil.
- **Sin dependencias nuevas** salvo `@axe-core/playwright` (dev, UI-22). Nada de MSW, react-query ni librerías de componentes (spec §8).

## Review Focus

Del plan maestro v2: ítem 1 (`test_every_route_requires_auth_except_public_routes` sigue verde con las rutas de UI-05 y UI-06) e ítem 2 (CSRF en `POST /api/reviews`, `PATCH /api/cards/{id}/flags`, `PUT /api/me/prefs`). Del subsistema (P09-n):

1. El cliente pone `X-CSRF-Token` en todo método no seguro y nunca en `GET`; ante `403 csrf` renueva con `GET /api/auth/me` y reintenta **una** vez. Test: UI-04 `csrf header only on unsafe methods and one retry after csrf 403`.
2. Un `401` en cualquier llamada deja la sesión en `anonymous` y lleva a `/entrar?next=…`; `next` solo acepta rutas de la app (empieza con `/`, no con `//` ni contiene `:`). Tests: UI-04 `401 calls onUnauthenticated once`, UI-08 `next only accepts same-app paths`.
3. El servidor valida el estado FSRS que manda el cliente (R-38), una reseña repetida (misma `reviewed_at`) no duplica `review_log` y una reseña más vieja que la última guardada es `409`. Tests: UI-05 `test_review_validation_r38`, `test_review_replay_is_idempotent_and_out_of_order_is_409`.
4. Una reseña hecha sin conexión queda en la cola, se envía una sola vez y en orden al volver la red; cerrar sesión con escrituras pendientes avisa antes, y al cerrar se borran las cachés de la API y la cola. Tests: UI-07 `flush sends in order and exactly once`, `purge clears api caches outbox and last me`; UI-08 `logout warns when outbox has pending writes`.
5. El service worker nunca guarda `/api/auth/*`, `/api/admin/*`, `/api/chat/*`, `/api/speech/*`, `/api/search` ni respuestas de métodos no `GET`, y la navegación nunca cae en `index.html` para `/api/`. Test: CHG-15 `api rules never cache private or unsafe routes`.
6. El build real no contiene el transporte demo, la instantánea ni las respuestas de quiz. Test: UI-21 `check-no-demo` sobre `npm run build` (y paso de CI en CHG-16).
7. El chat cancela con `AbortController`, muestra «pensando» con cronómetro y, si pasan 30 s sin primer token, un aviso sin cortar; nunca hay dos preguntas en curso desde la misma pestaña. Test: UI-18 `thinking timer, 30 s notice and cancel aborts the request`.
8. Ningún control interactivo mide menos de 44 × 44 px; axe no reporta violaciones `serious`/`critical` en ninguna pantalla en claro ni en oscuro; con movimiento reducido el volteo no anima. Tests: UI-02 `tokens pass AA in both palettes`; UI-22 `a11y.e2e.ts`.
9. Iniciar sesión con otro usuario en el mismo dispositivo borra antes los datos en caché del anterior. Test: UI-07 `different user on login purges previous user data`.
10. `/api/me/*` y `/api/review/*` solo leen y escriben datos del usuario de la sesión. Tests: UI-05 `test_queue_and_state_are_per_user`, UI-06 `test_stats_are_per_user`.

## Decisiones ante ambigüedades

1. **Numeración.** Las CHG nuevas siguen a la última existente (CHG-11, de P10): CHG-12…16. Las tareas del plan usan el prefijo `UI-` (UI-01…22). Si P11 agrega CHG en paralelo, el que fusione después renumera.
2. **Demo de Pages: se mantiene con API simulada, sin MSW.** Se descartó retirarlo (el repo es público y el demo es la única forma de ver la app sin cuenta; además los e2e necesitan una app sin servidor) y se descartó MSW (dependencia nueva, y su service worker choca con el de la PWA en el mismo `scope`). El demo v2 usa un `Transport` en el navegador (UI-21) sobre una instantánea JSON que genera **la API real** en proceso con `TestClient` sobre los fixtures sintéticos (UI-20); así el demo no puede divergir del contrato sin que falle UI-20. Los `GET` del demo son `fetch` reales a archivos estáticos, para que el service worker los guarde y el modo sin conexión se pruebe de verdad.
3. **E2E sobre el demo, no sobre el servidor.** Las cookies `__Host-…; Secure` no viajan sobre `http://localhost` en WebKit y `public_origin` exige `https` (CHG-07); levantar Caddy con TLS en CI es caro. La integración navegador–servidor se cubre con: los tests de API de P08/P10/P09 (TestClient `https`), la instantánea generada por la API real (UI-20) y el transporte demo que imita los códigos de error del servidor (401, 403 csrf, 404, 409). Un smoke contra el servidor real con TLS queda para P12 (go-live).
